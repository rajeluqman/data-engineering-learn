## 1. Concepts and definitions

**Eventual consistency, precisely re-scoped and renamed "convergence" [S]** (p334): "if you stop writing to the database and wait for some unspecified length of time, then eventually all read requests will return the same value." Named as "a very weak guarantee — it doesn't say anything about when the replicas will converge," making it "hard for application developers because it is so different from the behavior of variables in a normal single-threaded program."

**Linearizability, defined via the single-copy illusion and the football-score worked example [S]** (p336–337): "make a system appear as if there was only one copy of the data, and all operations on it are atomic." Its core content: "in a linearizable system, as soon as one client successfully completes a write, all clients reading from the database must be able to see the value just written" — "linearizability is a recency guarantee." The Alice/Bob world-cup example demonstrates a violation: Bob's query, issued after hearing Alice announce the score, still returns stale data because it hit a lagging replica.

**Linearizability's precise formalization via the register model, and its "flip must not go backwards" constraint [S]** (p338–340): illustrated via `read(x)⇒v` and `write(x,v)⇒r` operations on a shared register; reads concurrent with a write may legitimately return either old or new value, but the critical added constraint is that "once one client's read returns the new value, all subsequent reads must also return the new value" — preventing a value from appearing to flip back and forth. The formal test: operation "markers" (the instant each operation appears to take effect) must be joinable into a single sequential order that "always moves forwards in time... never backwards," and every read must return the value of the most recent prior write in that order.

**Serializability vs. linearizability, precisely and explicitly distinguished [S]** (p341–342): serializability is "an isolation property of transactions" spanning potentially multiple objects, guaranteeing behavior equivalent to *some* serial execution order — not necessarily the real-time order. Linearizability is "a recency guarantee on reads and writes of a register (an individual object)," says nothing about multi-object transactions, and does not by itself prevent write skew. A database providing both is called strict serializability / strong-1SR. Serializable snapshot isolation (SSI) is explicitly named non-linearizable, since by design it reads from a possibly-stale consistent snapshot.

**Linearizability's three named legitimate use cases [S]** (p342–344): locking/leader election (a distributed lock "must be linearizable: all nodes must agree which node owns the lock, otherwise it is useless" — the basis of ZooKeeper/etcd-backed coordination); uniqueness/constraint enforcement (usernames, account balances, stock levels, seat bookings) — though the chapter explicitly notes several of these can instead tolerate a "compensating transaction" (an apology workflow) rather than requiring true linearizability; and cross-channel timing dependencies, illustrated via an image-thumbnail pipeline where a message queue and a file-storage service form two separate communication channels, and a non-linearizable storage service can let the resizer fetch a stale (or missing) image — "analogous to" the Alice/Bob race.

**Which replication methods can be linearizable, an explicit per-method verdict [S]** (p345–346): single-leader replication is "potentially linearizable" if reads go to the leader or a synchronously-updated follower, but not guaranteed by design (e.g. snapshot-isolation-based leaders) and vulnerable to a "delusional leader" continuing to serve after being ousted; consensus algorithms (ZooKeeper, etcd) *are* linearizable, since they explicitly guard against split-brain and stale replicas; multi-leader replication is "generally not linearizable," since concurrent writes on multiple nodes require conflict resolution; leaderless (Dynamo-style) replication is "probably not linearizable" even with strict quorums (w+r>n) — LWW clock-skew, sloppy quorums, and even strict-quorum race conditions (worked in Figure 9-6) all break it, and a linearizable compare-and-set specifically "cannot" be built this way without a consensus algorithm.

**The CAP theorem, precisely scoped and its narrowness explicitly stressed [S]** (p348–350): the practical trade-off — "if your application requires linearizability, and some replicas are disconnected... they must either wait until the network problem is fixed, or return an error... they become unavailable," whereas an application not requiring linearizability "can remain available in the face of a network problem, but its behavior is not linearizable." CAP's formal scope is explicitly narrow: "it only considers one consistency model (namely linearizability) and one kind of fault (network partitions)... it doesn't say anything about network delays, dead nodes, or other trade-offs." Explicit verdict: "CAP has little practical value for designing systems" and "is best avoided" as a design framework, though it deserves credit for the mid-2000s NoSQL "culture shift."

**Linearizability's fundamental performance cost, an explicit proven limit [S]** (p351): Attiya and Welch prove that "if you want linearizability, the response time of read and write requests is at least proportional to the uncertainty of delays in the network."

Explicit consequence (p351): "linearizability is slow" — this is true all the time, not only during a network fault — and a faster algorithm for linearizability does not exist. `[D]` Even multicore CPU RAM is explicitly named non-linearizable (per-core caches), for performance reasons unrelated to fault tolerance — "the reason for dropping linearizability is performance, not fault tolerance," in that specific case.

**Causal order, defined as a partial order distinguished from linearizability's total order [S]** (p353–354): "a total order allows any two elements to be compared"; causality instead defines "a partial order: some operations are ordered with respect to each other, but some are incomparable" (concurrent). Central relationship: "linearizability implies causality: any system that is linearizable will preserve causality correctly," but the converse doesn't hold — a system can be causally consistent without paying linearizability's performance cost, and "causal consistency is the strongest possible consistency model that does not slow down due to network delays, and remains available in the face of network failures."

**"Watch your causality," the chapter's own explicit unifying thesis [S]** (p353): "many of the last 200 pages of this book could be boiled down to the three words" of that phrase — tying together read skew, write skew, consistent-prefix-reads, and the football-score/thumbnail examples as instances of the same underlying causal-ordering concern. `[D]`

**Lamport timestamps, defined as the causally-consistent sequence-number scheme, contrasted with three named non-causal generators [S]** (p357–359): three naive schemes (per-node odd/even counters, physical-clock timestamps, pre-allocated ID blocks) each fail to be causally consistent because none tracks cross-node knowledge. Lamport's fix: each `(counter, node ID)` pair timestamp is compared by counter first, node ID as tiebreaker, and critically "every node and every client keeps track of the maximum counter value it has seen so far, and includes that maximum on every request" — forcing any causally-later operation to receive a strictly greater timestamp. Explicitly distinguished from version vectors: Lamport timestamps give total order but cannot distinguish concurrency from causal dependency, whereas version vectors can distinguish concurrency but don't give a total order.

**Timestamp ordering's fundamental insufficiency, demonstrated via the username-uniqueness problem [S]** (p359–360): even a fully causally-consistent total order (Lamport timestamps) cannot resolve a live uniqueness check, because "the total order of operations only emerges after you have collected all of the operations" — at decision time, a node cannot know whether another node is concurrently about to claim a lower timestamp for the same key. Explicit conclusion: "it's not sufficient to have a total ordering of operations — you also need to know when that order is finalized," which is exactly what total order broadcast provides.

**Total order broadcast, defined by two named required properties [S]** (p361): reliable delivery ("no messages are lost: if a message is delivered to one node, it is delivered to all nodes") and totally ordered delivery ("messages are delivered to every node in the same order"), with the critical added property that "the order is fixed at the time the messages are delivered" — a node cannot retroactively insert a message earlier once later messages have already been delivered, which is exactly what timestamp ordering alone cannot guarantee.

**Total order broadcast's equivalence to a linearizable register/consensus, and its use for state machine replication [S]** (p362–364): total order broadcast can implement a linearizable compare-and-set register (append a tentative claim to the log, wait for it to be delivered back, check whether your own message is first) and vice versa (increment-and-get a linearizable counter to generate gap-free sequence numbers for broadcast). "It can be proved that a linearizable compare-and-set (or increment-and-get) register and total order broadcast are both equivalent to consensus" — "a profound and surprising insight." Total order broadcast underlies state machine replication (Ch.11 forward reference) and can implement serializable transactions when combined with deterministic stored-procedure execution.

**Consensus, formally defined by four named properties [S]** (p377): uniform agreement ("no two nodes decide differently"), integrity ("no node decides twice"), validity ("if a node decides value v, then v was proposed by some node" — ruling out trivial "always decide null" solutions), and termination ("every node that does not crash eventually decides some value" — the one liveness property among four, the other three being safety properties). A single hard-coded "dictator" node trivially satisfies the first three but fails termination the moment it fails — "this is, in fact, what we saw in the case of 2-phase commit."

**Consensus's majority requirement and Byzantine-fault exclusion, both explicit named limits [S]** (p378): "any consensus algorithm requires at least a majority of nodes to be functioning correctly in order to assure termination" — but safety properties (agreement, integrity, validity) are guaranteed unconditionally "even if a majority of nodes fails or there is a severe network problem," so an outage can only halt progress, never corrupt the decision. Most practical consensus algorithms (Paxos, Raft, Zab, VSR) assume no Byzantine faults, consistent with Ch.8's standing assumption.

**The FLP impossibility result, precisely scoped to explain why impossible consensus is nonetheless practically solvable [S]** (p366): the Fischer-Lynch-Paterson result proves no algorithm can reliably achieve consensus if a node may crash, but this holds "in a very restrictive theoretical system model, assuming a deterministic algorithm that cannot use any clocks or timeouts."

Allowing timeouts (or even just randomness) makes consensus solvable in practice — the impossibility result remains of great theoretical importance but doesn't block real-world consensus algorithms (p366). `[D]`

**Two-phase commit (2PC), defined by its coordinator/participant roles and its two named "points of no return" [S]** (p367–370): a coordinator sends a `prepare` request to every participant (phase 1); only if all reply "yes" does it send `commit` in phase 2, otherwise `abort`. Two irrevocable moments make atomicity work: a participant voting "yes" promises unconditionally that it can commit later ("the participant gives up the right to abort the transaction, but without actually committing it"), and once the coordinator writes its decision to its own transaction log — the "commit point" — that decision "is final" and must be enforced via indefinite retries.

**2PC's in-doubt/blocking failure mode, an explicit named structural weakness [S]** (p370–371): if the coordinator crashes after a participant has voted "yes" but before that participant hears the final decision, the participant enters an "in doubt" or "uncertain" state and "can do nothing but wait" — neither unilateral commit nor unilateral abort is safe, since the coordinator's actual decision (possibly already partially executed on other participants) is unknown. "The only way how 2PC can complete is by waiting for the coordinator to recover," making 2PC formally a *blocking* atomic commit protocol.

**Three-phase commit (3PC), named as 2PC's non-blocking alternative and explicitly judged impractical [S]** (p372): "the standard formulation of 3PC assumes a network with bounded delay and nodes with bounded response times," which real, partially-synchronous systems don't provide, so "in most practical systems... it cannot guarantee atomicity." Non-blocking atomic commit in general "requires a perfect failure detector," which a timeout-based system in an unbounded-delay network cannot supply — hence 2PC "continues to be used, despite the known problem of blocking on coordinator failure."

**Distributed transactions' two named distinct categories, with sharply different practical viability [S]** (p372–373): database-internal distributed transactions (VoltDB, FoundationDB, MySQL Cluster NDB — all participants run the same software) "can often work quite well," since implementation-specific optimizations and full protocol compatibility are possible; heterogeneous distributed transactions (spanning different vendors/technologies, e.g. XA) are "a lot more challenging" because they must reduce to a lowest-common-denominator protocol.

**XA transactions, defined as the standard mechanism for heterogeneous 2PC, with its lock-holding cost stated explicitly [S]** (p374–375): a C API (not a network protocol) letting a shared coordinator library drive `prepare`/`commit`/`abort` callbacks across drivers for different databases/message brokers. Critical operational cost: "the database cannot release those locks until the transaction commits or aborts... a transaction must hold onto the locks throughout the time it is in doubt" — a crashed coordinator can hold locks "for 20 minutes," or "forever" if its log is lost, "at least until the situation is manually resolved by an administrator."

**Heuristic decisions, named an explicit "emergency escape hatch" that breaks atomicity [S]** (p375): letting a stuck participant unilaterally commit or abort an in-doubt transaction without the coordinator's final word — "heuristic here is a euphemism for probably breaking atomicity, since it violates the system of promises in 2-phase commit," intended "only for getting out of catastrophic situations, and not for regular use."

**Distributed transactions' three named structural limitations beyond the in-doubt lock problem [S]** (p376): a non-replicated coordinator is a single point of failure for the entire distributed transaction; a coordinator embedded in an otherwise-stateless application server makes the coordinator's log "as important as the databases themselves," breaking the stateless-application-server model; and XA's lowest-common-denominator nature prevents cross-system deadlock detection and is incompatible with SSI. A more general structural cost: "distributed transactions thus have a tendency of amplifying failures" — since 2PC requires all participants to respond, any single broken participant fails the whole transaction.

**Epoch numbers and quorum voting, the chapter's own mechanism explaining how consensus algorithms break the "need a leader to elect a leader" circularity [S]** (p380–381): every leader election is tagged with a strictly increasing epoch number (ballot number in Paxos, view number in VSR, term number in Raft); within an epoch the leader is guaranteed unique, and if two leaders from different epochs conflict, "the leader with the higher epoch number prevails." Before deciding anything, a leader must confirm via a majority vote that no higher-epoch leader exists — since both leader election and value-proposal each require a majority, and majorities always overlap by at least one node, at least one voter will have seen any more-recent leader election, preventing a stale leader from making a conflicting decision.

**Consensus algorithms vs. 2PC, the key structural difference stated explicitly [S]** (p381): "fault-tolerant consensus algorithms only require votes from a majority of nodes, whereas 2PC requires a yes vote from every participant" — plus consensus algorithms define an explicit recovery process for reaching a consistent state after a new leader is elected, which 2PC lacks entirely.

**Consensus's four named practical costs, despite its safety and fault-tolerance benefits [S]** (p381–382): voting-before-deciding is effectively synchronous replication, so some committed data can still be lost if async replication would otherwise have been preferred for performance; a strict majority is always required (3 nodes tolerate 1 failure, 5 tolerate 2), so a network split leaves the minority partition fully blocked; most implementations assume a fixed, static node membership (dynamic-membership extensions exist but are "much less well understood"); and reliance on timeouts for failure detection means highly variable network delays (especially geographically distributed deployments) can trigger frequent, performance-destroying false leader elections — Raft specifically is named to have a documented pathological case where "leadership continually bounces between two nodes" under one specific unreliable link.

**ZooKeeper/etcd's role, defined as an "outsourced" bundle of four named coordination primitives [S]** (p382–383): linearizable atomic operations (compare-and-set-based locks/leases); total ordering of operations (via a monotonically increasing transaction ID/version, directly usable as a fencing token — Ch.8's cross-reference); failure detection (session heartbeats with automatic ephemeral-node cleanup on timeout); and event notifications (subscribable watches avoiding client polling). Explicit note: "of these features, only the linearizable atomic operations really require consensus" — but the *combination* is what makes these systems broadly useful for coordination tasks like leader election and partition-to-node assignment.

**Service discovery vs. leader election, explicitly distinguished on whether consensus is actually required [S]** (p384): "it is less clear whether service discovery actually requires consensus" — DNS-style lookup tolerates staleness and prioritizes availability/robustness over linearizability. "Although service discovery does not require consensus, leader election does" — motivating read-only, non-voting caching replicas in some consensus systems that serve non-linearizable reads of "who is currently leader" without participating in the underlying vote.

## 2. WHAT / WHY / WHEN

**WHAT:** a systematic reduction argument showing that a wide, seemingly-unrelated set of distributed-systems problems — linearizable registers, atomic transaction commit, total order broadcast, distributed locks/leases, membership/failure detection, and uniqueness constraints — are all formally equivalent to, or reducible from, the single problem of consensus, and a survey of the practical algorithms (2PC, epoch-based majority-vote consensus) and coordination services (ZooKeeper, etcd) that solve it. `[D]`

**WHY it matters:** every "impossible-seeming" distributed guarantee discussed earlier in the book (leader election without split-brain, cross-partition atomic transactions, a uniqueness constraint enforced live) collapses to the same underlying problem, so understanding consensus's actual cost (majority requirement, synchronous-replication-like voting, timeout sensitivity) explains precisely why systems that need these guarantees pay a real, unavoidable performance and availability price — and conversely, why systems that avoid consensus (leaderless/multi-leader replication, eventually-consistent stores) trade away exactly these guarantees on purpose, not by oversight. `[D]`

**WHEN to require linearizability/consensus vs. accept causal consistency or eventual consistency, synthesized across the chapter (p320–333, p359–365):** require linearizability/consensus specifically for distributed locks and leader election, uniqueness constraints that must be enforced live rather than resolved after the fact, and atomic cross-partition/cross-system commits where partial application is unacceptable; accept causal consistency when preserving cause-and-effect ordering matters (avoiding read-skew-like anomalies across communication channels) but full recency/total-ordering is not required, since it avoids consensus's network-delay-proportional cost entirely; accept eventual consistency / abandon consensus altogether when availability under partition and low latency matter more than any live agreement guarantee, accepting that conflicts (write skew, concurrent uniqueness violations) must instead be resolved after the fact via compensating transactions or apology workflows.

## 4. Mechanism / key steps

**2PC's full commit protocol, the chapter's own worked six-step description (p369–370)** `[D]`: application requests a globally unique transaction ID from the coordinator → application begins a single-node transaction on each participant tagged with that ID, doing all reads/writes there → coordinator sends `prepare` to all participants when the application is ready to commit, aborting immediately if any prepare fails or times out → each participant durably writes all transaction data and checks constraints before voting to proceed, thereby promising unconditional future commit ability → once every participant's vote is in favor, the coordinator durably writes its commit/abort decision to its own log (the commit point) → the coordinator sends the final commit/abort instruction to all participants, retrying indefinitely until every participant acknowledges, with recovery-time participants honoring their earlier vote unconditionally.

**Epoch-based leader consensus's majority-overlap safety argument, the chapter's own worked description (p380–381)** `[D]`: every leader election increments a global epoch number → a leader must win a majority vote to take office in its epoch → before deciding any proposed value, the leader must again get a majority of nodes to vote in favor, and a node only votes yes if it is unaware of any higher-epoch leader → because both the election and every subsequent proposal each require a majority, and any two majorities among the same node set must overlap by at least one node → that overlapping node necessarily knows about the most recent leader election → therefore a leader that successfully wins a proposal vote can be certain no newer leader has since taken over, breaking the circularity of needing a leader in order to elect a leader without an infinite regress.

## 5. Trade-offs and limitations

- **Linearizability buys a simple, single-copy mental model but at a proven, unavoidable latency cost proportional to network delay uncertainty — and it becomes fully unavailable under a network partition for any replica cut off from the majority/leader (§1, p326–329):** an explicit, named, mathematically proven trade-off (Attiya and Welch), not merely an engineering inconvenience.
- **2PC solves atomic commit across heterogeneous systems but introduces a hard blocking failure mode (in-doubt transactions holding locks indefinitely) that 3PC cannot practically fix given real networks' unbounded delays (§1, p348–350):** the chapter frames this as evidence that atomic commit's cost is structural, not an implementation defect — non-blocking atomic commit provably requires a perfect failure detector that asynchronous networks cannot supply.
- **Consensus algorithms are safe and fault-tolerant but always require a strict majority, meaning a network partition leaves the minority side fully unable to make progress, and static-membership assumptions make cluster resizing awkward (§1, p359–360):** an explicit, named structural cost accepted in exchange for consensus's safety guarantees, distinct from — and in addition to — the general CAP-style availability trade-off.
- **Causal consistency avoids linearizability's performance/availability cost while still preventing the most confusing anomalies (read skew, cross-channel races), but cannot alone solve problems requiring a finalized total order (e.g. live uniqueness enforcement) — those problems reduce irreducibly to consensus (§1, p332–338):** causal consistency is explicitly framed as the strongest available "free lunch" consistency model, with total order broadcast/consensus as the necessary (and costly) next step only when that isn't enough.

## 6. Failure modes and edge cases

- **The football-score cross-replica staleness anomaly (§1, p314–315):** a concrete, memorable illustration of a linearizability violation with real user-facing confusion, used as the chapter's recurring reference case throughout the rest of the chapter (re-invoked for the thumbnail-pipeline and Lamport-timestamp examples).
- **Strict-quorum non-linearizability despite w+r>n (§1, p324–325, Figure 9-6):** a writer completing a w=3 write and two readers with r=2 quorums can still observe a linearizability violation — one reader sees the new value, a later-starting reader sees only the old value — demonstrating that quorum overlap alone (without synchronous read repair and write-side quorum re-verification) does not guarantee linearizability, contrary to a common assumption.
- **A "delusional leader" continuing to serve stale/incorrect reads after being ousted, breaking linearizability even under nominally single-leader replication (§1, p323):** directly connects to Ch.8's "truth is defined by majority" material — a node's own belief that it is leader is not sufficient grounds for the system to treat its output as linearizable.
- **Orphaned in-doubt XA transactions surviving even a full reboot, requiring manual administrator resolution under production-outage time pressure (§1, p353):** a concrete named operational failure mode — a lost or corrupted coordinator log leaves locks held "forever," and only a human, examining every participant's actual state, can safely resolve the transaction, since a correct 2PC implementation must preserve in-doubt locks across reboots to avoid risking an atomicity violation.
- **Raft's pathological single-unreliable-link leadership-bouncing case (§1, p360):** a documented edge case where one persistently flaky network link (not a full partition) causes leadership to perpetually oscillate between two nodes, or the current leader to be perpetually forced to resign, so the system "effectively never makes progress" despite most of the network functioning correctly.

## 7. Implications for design / build / maintain / RCA / optimization

- **Design:** the linearizability-vs-causal-consistency-vs-eventual-consistency decision framework (§2) is directly reusable for choosing a consistency model for any new distributed component in this vault's projects, driven by whether the specific guarantee needed is recency (linearizability), cause-effect ordering (causal), or neither (eventual). `[D]`
- **Build:** the "is this problem reducible to consensus?" checklist (§1, summary list: linearizable CAS, atomic commit, total order broadcast, locks/leases, membership, uniqueness constraints) is directly reusable to recognize when a from-scratch implementation attempt should instead delegate to an existing coordination service (ZooKeeper/etcd) rather than reinventing a consensus algorithm, which the chapter explicitly warns "has a poor success record."
- **Maintain:** the XA in-doubt-transaction operational risk (§1, §6, p352–353) is a directly reusable pre-mortem checklist item for any system deploying heterogeneous distributed transactions — specifically, ensure the transaction coordinator itself is treated with database-grade durability/replication care, since its log becomes as critical as any participant database's data.
- **RCA:** a distributed lock or leader-election system observed to "flap" (frequent leadership changes with no obvious full outage) is directly diagnosable against the Raft single-flaky-link pattern (§6, p360) — check for one specific unreliable network path rather than assuming a full network partition or hardware failure.
- **Optimization:** the "consensus voting is effectively synchronous replication" framing (§1, p359) is a directly reusable lens for explaining observed latency/throughput costs in any ZooKeeper/etcd-backed coordination path — the fix is not to "tune" the consensus system but to minimize how often and how much data flows through it (e.g. use it only for slow-changing coordination metadata, not high-frequency application state, exactly as the chapter recommends).

## 8. How to test / verify these claims

- The strict-quorum non-linearizability claim (§1, p324–325) is directly reproducible: construct the chapter's own Figure 9-6 scenario against a real Dynamo-style store (e.g. Riak or Cassandra) with n=3, w=3, r=2, using controlled network delay injection, and confirm a later-starting reader can observe a stale value while an earlier-starting concurrent reader observes the new one.
- The Attiya-Welch linearizability-latency claim (§1, p328–329) is directly testable: measure read/write response times for a linearizable store (e.g. ZooKeeper, or etcd with quorum reads) versus a non-linearizable eventually-consistent store under the same injected network-delay variability, and confirm the linearizable store's latency scales with delay uncertainty.
- The 2PC in-doubt blocking claim (§1, p348–349, §6) is directly reproducible: run a distributed transaction across two XA-compliant databases, kill the coordinator process after participants have voted "yes" but before the final decision is sent, and confirm the participant transactions remain blocked (holding locks) until the coordinator is manually restarted and its log read.
- The epoch/majority-vote safety argument (§4, p358–359) is directly testable by construction: force a network partition splitting a 5-node Raft or ZooKeeper cluster into a 3-node and 2-node group, confirm only the 3-node majority side elects a leader and makes progress, and confirm the 2-node minority side remains blocked and never diverges.
